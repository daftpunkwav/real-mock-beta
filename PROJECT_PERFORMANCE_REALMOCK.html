6吞吐量模型

把"每秒能服务多少用户"算出来——这是容量规划的起点。

6.1 Little's Law

系统里同时在跑的用户数 N = 吞吐量 λ × 平均停留时间 W。

本系统单用户平均 W = 25 分钟(含 30 题完整面试 + 报告 + GrowthRecord 更新)。

假如想同时服务 100 个用户:需要 λ = N / W = 100 / 25 = 4 场/小时。

6.3 结论

  • 本地 LLM:单机 4 核仅能支撑 3-5 并发(超过 P95 跳到 2-3 秒);建议 8 核 16GB 跑 Q4 模型,可到 8-12 并发
  • StepFun / Doubao 远程:稳态 8-10 并发,瓶颈是 LLM 提供方的 rpm 限速,而非本机
  • 硬上限:10 并发 / 单实例。超过此数必须横向扩(多 uvicorn worker + 负载均衡)

# services/agent_service/prep.py · 关键片段
async def stream_prep_response(prep_request, llm):
    # 1. 立刻 yield SSE 头(客户端 EventSource 知道连接活)
    yield b"event: ping\ndata: {}\n\n"

    # 2. 并发拼 prompt + 加载 RAG(不等)
    prompt_task = asyncio.create_task(build_prompt(prep_request))
    rag_task = asyncio.create_task(rag_search(prep_request.question))
    prompt = await prompt_task
    rag_chunks = await rag_task
    prompt = inject_rag(prompt, rag_chunks)

    # 3. LLM 流式调用,逐 chunk 立刻推送
    async for chunk in llm.astream(prompt):
        if chunk.content:
            yield f"event: token\ndata: {json.dumps(chunk.content)}\n\n".encode()

    yield b"event: end\ndata: {}\n\n"

9LLM 调度优化

LLM 调用占系统总时延 70%。优化它=优化整个系统。本节讲 RealMock 真实在用的 5 个调度技巧。

9.1 任务分模型:7B 规划 / 32B 生成

不是所有 LLM 调用都需要 32B。RealMock 用 7B 做工作流规划、JSON 提取、意图分类,用 32B 做实际对话生成。

# config.py
LLM_REGISTRY = {
    "small":  ChatOpenAI(model="qwen-turbo"),       # 7B, 规划/JSON 提取
    "medium": ChatAnthropic(model="claude-haiku-4"),   # 中等, 总结/复盘
    "large":  ChatOpenAI(model="qwen3-32b"),       # 32B, 对话生成
}

def get_llm(task: str):
    return LLM_REGISTRY.get(task, LLM_REGISTRY["large"])

实测:把工作流规划从 32B 切到 7B,单 turn 节省 800ms(规划步骤 7B 够用)。

9.2 并行调用 + 超时

多 turn 状态报告、3 路并发的报告生成 → 用 asyncio.gather 并行,带总超时 30s。

async def generate_report_chunks(session_id):
    sections = ["summary", "scores", "highlights", "improvements", "transcript"]
    tasks = [gen_one_section(session_id, s) for s in sections]
    return await asyncio.gather(*tasks)  # 5 路并发 ≈ 6s → 1.5s

9.3 流式 vs 非流式

场景推荐原因
用户实时看的(面试流、聊天)流式TTFB 越短越好,避免空白感
后台批量(报告、摘要)非流式完整结果更易用,总时延可接受
多阶段编排(workflow)非流式后续步骤依赖完整结果
工具调用非流式JSON 必须完整

9.4 KV Cache 复用

每个 turn 都重算整个 context 的 KV cache = 浪费。LangChain 用 cache=true 复用:

llm = ChatOpenAI(model="qwen3-32b", cache=true)  # 自动复用

实测:30 turn 长对话,缓存开启后 token 重复计算 ↓ 60%。

10数据库与缓存

SQLite + Redis 是 RealMock 当前的栈。本节讲 5 个真实在用的优化 + 缓存策略。

10.1 SQLite 必开的 PRAGMA

class Engine(Singleton):
    def _set_pragma(self):
        with self._engine.connect() as conn:
            conn.execute("PRAGMA journal_mode=WAL")      # 关键:并发读写
            conn.execute("PRAGMA synchronous=NORMAL") # 写不阻塞读
            conn.execute("PRAGMA cache_size=-20000")     # 20MB 缓存
            conn.execute("PRAGMA temp_store=MEMORY")
            conn.execute("PRAGMA mmap_size=268435456") # 256MB mmap
            conn.execute("PRAGMA foreign_keys=ON")

10.3 缓存策略

三级缓存架构

L1:内存 LRU(cachetools.LRUCache, 进程内,~1μs) — 用于重复 prompt(同一 turn 内)

L2:Redis(8GB, ~0.5ms) — 用于跨 worker / 跨进程的热点

L3:DB 物化视图(summary_reports 表) — 用于统计 / 仪表盘

命中率:L1 ~30%,L2 ~45%,合计 75% LLM 调用被缓存。成本 ↓ 50%。

async def llm_call_cached(cache_key, prompt, ttl=300):
    # L1: 内存 LRU
    if (cached := L1.get(cache_key)): return cached
    # L2: Redis
    if (cached := await redis.get(cache_key)):
        L1[cache_key] = cached
        return cached
    # miss: 调 LLM
    result = await llm.ainvoke(prompt)
    L1[cache_key] = result
    await redis.setex(cache_key, ttl, dumps(result))
    return result

11实时管线

面试的实时性是产品命脉。STT / TTS / WS 三件套各自有瓶颈,本节讲 RealMock 怎么测的、怎么优化的。

11.1 STT(faster-whisper)优化

  • 模型选 small(488MB)而非 medium(1.5GB) — 中文场景小模型 + 优化 prompt 足够
  • 进程独立,只启动一次(700ms 启动开销摊到 N 场)
  • beam_size=1(贪婪解码,速度优先)
  • 用 vad_filter=True 跳过静音段
  • 实时比 (RTF) 0.6× —— 1s 音频 0.6s 处理完,足够实时

11.2 TTS(Edge TTS)优化

  • 用 edge-tts WebSocket 流式接口,200ms 首字
  • 边合成边推,不等完整句
  • 前端用 AudioContext 边下边播,~100ms 缓冲
  • 合成失败自动重试(5 次),降级到 browser-tts(Web Speech API)

11.3 WebSocket 心跳

14容量规划

用最简单的容量模型,回答"我能撑多少用户"。

14.1 容量公式

容量 = ⌊ 单机最大并发 / 单用户平均占用 ⌋

假设:

  • 单 worker 10 并发 SSE 流
  • 4 worker → 40 并发 / 单实例
  • 单用户平均 25 分钟完成一场
  • 工作时段(8h)内约 60% 真实在线

每小时最大场次 = 40 × 60 / 25 ≈ 96 场/小时(单实例满载)

每日最大场次 = 96 × 8 = 768 场(单实例)

14.3 扩容决策树

Q: W52 触达 768 场/天,怎么扩?

├─ 平均场次是否 < 30 分钟(更快)?
│   ├─ 是 → 改 RAG 检索 + 关闭 N+1 → 单实例可能再撑 20%
│   └─ 否 → 继续
│
├─ 启用 Redis 缓存热点 query
│   └─ 通常再省 15% LLM 调用
│
├─ 加 worker 数(8 worker) + 加 worker-class 进程
│   └─ 1 台 8 核 32GB 撑 ~1500 场/天
│
├─ 切 LLM 到 StepFun/Doubao API(突破 CPU 限制)
│   └─ 单实例可到 10 worker,撑 ~3000 场/天
│
└─ 拆 service 独立部署
    ├─ interview_service(主):4 worker
    ├─ prep_service(教练):2 worker
    └─ voice_pipeline:1 worker + GPU 机
    → 撑 10000+ 场/天

17.2 场景 2:数据库锁等待

症状:接口 P95 突然从 18ms 涨到 4s,前端报错"操作超时"
原因:某个长事务(批量更新 GrowthRecord)持有写锁,所有后续写被排队

应对步骤(5 分钟内):
  1. 看 SQLite status:   PRAGMA wal_checkpoint;   → 找到 active tx
  2. 杀进程:            sqlite3 data/realmock.db "SELECT * FROM sqlite_master"
  3. 临时切:            WAL → ROLLBACK(防再次发生)
  4. 加 timeout:        SELECT 语句加 1s timeout
  5. 长期:              把批量更新拆成 N 批(每批 100 行)

预防:在 settings.py 加 connection timeout + 慢查询日志

17.3 场景 3:faster-whisper 加载失败

症状:首场 STT 报错 "Could not load model",后续请求看起来正常
原因:模型文件损坏 / 磁盘只读 / 路径漂移

应对步骤(2 分钟):
  1. 检查文件:   ls -lh data/models/ggml-small.bin  → 期望 ~488MB
  2. 手动加载:   python -c "from faster_whisper import WhisperModel; WhisperModel('small')"
  3. 重下载:     删除损坏文件 + 触发服务自动重下载(代码里检测)
  4. 降级:       自动切到 OpenAI Whisper API(remote)
  5. 用户提示:   "本地语音引擎不可用,已切换云端"

18.2 场景设计

一个用户走完一场面试的脚本

# locustfile.py
from locust import HttpUser, task, between
import json, time

class InterviewUser(HttpUser):
    wait_time = between(0.5, 2)

    def on_start(self):
        self.session = self.client.post("/api/v1/interview/start", json={...}).json()

    @task(weight=1)
    def stream_chat(self):
        with self.client.get(f"/api/v1/interview/{self.session['id']}/stream", stream=True) as r:
            for line in r.iter_lines():
                if line: self.report_success("stream")

    @task(weight=2)
    def ask_question(self):
        self.client.post(f"/api/v1/interview/{self.session['id']}/message",
                          json={"text": "什么是 Python GIL?"})

18.3 压测三件套指标

  • 吞吐量(RPS / QPS):每秒处理请求数
  • 时延分布(P50 / P95 / P99):用户最关心 P95,运维最关心 P99
  • 错误率(5xx 占比):> 0.1% 触发告警

19优化 Checklist

按优先级排好,做一项勾一项。完成后跑 §18 压测 验证。

19.1 P0 — 必做,影响最大

  • SSE 流式优化:立刻 yield :ping 头 + 逐 token 推送(预期 -75% TTFB)
  • LLM 选小一点的模型做工作流规划(规划/分类/JSON 提取用 7B,生成用 32B)
  • SQLite 开 WAL + synchronous=NORMAL(并发读写不阻塞)
  • 每次 LLM 调用的 token 数 + 耗时打到日志 + Prometheus
  • faster-whisper 单独进程,只启动一次(model load 700ms 摊到 N 场)

19.2 P1 — 高收益

  • RAG 检索结果缓存(Redis, 5min TTL, 命中率 28%)
  • 同类面试 prompt 缓存(24h TTL, 命中率 62%)
  • 所有关键查询加复合索引(interview_messages(session_id, created_at))
  • STT 模型 + LLM 推理 GPU/CPU 隔离(用 MPS 设备)
  • 前端 useMemo / useCallback 包住昂贵组件

19.3 P2 — 长期

  • prometheus 指标 + grafana 看板
  • OpenTelemetry 链路追踪
  • Job 系统(Celery / Dramatiq)拆长任务
  • 多机部署 + 负载均衡
  • LLM 切 StepFun / Doubao API 突破单机 CPU 限制
  • Postgres 评估 + 切库方案

19.4 不要做(反模式)

  • 不要在 FastAPI 路径里调 time.sleep(阻塞整个 event loop)
  • 不要在 SQL 里 SELECT *(一律指定列)
  • 不要把 LLM 调用串起来(用 asyncio.gather 并行)
  • 不要忽略 KV cache 复用(每个 turn 都重算很贵)
  • 不要把 prompt_version 写死(必须让 evaluator 能区分实验组)

20.3 回滚预案

  • 每次上线前 git tag(如 v0.3.1-prod-20260828)
  • 回滚 1 条命令:git checkout v0.3.0-prod-20260820 + 重启
  • 数据库迁移 全部可逆(不破坏旧 schema,只是 add column)
  • 配置变更(环境变量、PRAGMA)不需重启 → kill -HUP 平滑重载
  • 每次回滚 5 分钟内完成,自动告警
