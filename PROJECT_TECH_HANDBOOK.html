1LLM 基础:Token / Context Window

AI 基础

核心概念

Token = LLM 处理的最小单元,不是字符也不是单词,而是 BPE 等算法切出的"片段"。中文约 1 字符 = 1.5 token,英文 1 词 ≈ 1.3 token。Context Window 是模型一次能"看见"的最大 token 数,超出部分会被截断或压缩。

RealMock 中的用法

shared/capabilities/ai/context_manager.pytoken 估算
def estimate_tokens(text: str) -> int:
    # 中文约 1.5 字符/token 的粗略估计
    if not text: return 0
    return max(1, int(len(text) / 1.5))

def compress_messages(messages, max_tokens, *, keep_recent=20, threshold=0.3):
    # 阈值 30% 触发压缩：保留 system + 最近 20 条 + 压缩说明
    total = estimate_messages_tokens(messages)
    if total <= max_tokens * threshold: return messages
    system = [m for m in messages if m.get("role") == "system"]
    rest = [m for m in messages if m.get("role") != "system"]
    trimmed = rest[-keep_recent:]
    summary = {"role": "system", "content": f"[上下文压缩] 早期 {len(rest) - len(trimmed)} 条对话已省略,保留最近 {len(trimmed)} 条。"}
    return system + [summary] + trimmed

prompt_assembler.get_context_window 在每回合动态读取"思考"阶段的 context_window 设置,把超出预算的旧消息压掉。

为什么 context 重要?

  • 过短 → LLM 忘记前文(典型的"长会话失忆")
  • 过长 → 推理变慢 + 成本线性增长 + 模型注意力衰减
  • 系统提示必须始终保留(不可压缩),否则行为漂移

实战技巧:context 满之前就要触发压缩(项目里 30% 阈值)。不要等超限再压,那时已经丢失信息。

Prompt 优化的常见坑

❌ 不要

  • 只靠自然语言约束(模型会"忘记")
  • 规则之间相互冲突
  • 系统提示超长(挤占对话上下文)
  • 假设模型"知道"上下文(它不会跨请求)

✅ 推荐

  • 结构化输出(JSON schema / response_format)
  • 每个 prompt 末尾追加 hard constraint
  • 少示例好过多示例(few-shot 选典型反例)
  • 用 [PHASE_COMPLETE] 这类机器可读的控制标记解析状态

3Function Calling

AI 基础

核心概念

Function Calling(也叫 Tool Use)让 LLM 在生成回复时,可以决定"现在我需要调用某个外部工具"。模型输出的是结构化的工具调用请求(不是真的执行),由应用层实际执行,再把结果以 tool 角色消息回喂给模型。

OpenAI 协议中的 tool message 流程

应用messages = [system, user(查询 SQL 表的订单)];tools = [{name: "query_db", parameters: {sql: string}}] → OpenAIPOST /chat/completions OpenAI→ 返回 finish_reason=tool_calls;choices[0].message = {role: assistant, content: null, tool_calls: [{id: "call_1", type: "function", function: {name: "query_db", arguments: '{"sql": "SELECT * FROM orders"}'}}]} 应用解析 tool_calls,实际执行 SQL;追加 messages += {role: tool, tool_call_id: "call_1", content: "<实际结果>"} 应用 → OpenAI再次 POST,带新 messages OpenAI→ 返回正常的 assistant 文本,引用工具结果

async def run_tool_rounds(self, api_messages, db, *, temperature=0.75):
    # 1) 是否启用工具?配置 / 轮数限制
    if not settings.interview_tools_enabled: return api_messages, None
    max_rounds = min(settings.interview_max_tool_rounds, MAX_TOOL_ROUNDS)  # 默认 3
    if max_rounds <= 0: return api_messages, None

    tools = self.collect_chat_tools(include_function_tools=True)
    if not tools: return api_messages, None

    working = list(api_messages)
    any_tool_used = False
    for round_i in range(max_rounds):
        # 2) 调 LLM,期望 tool_calls
        msg = await self.llm.chat_message(working, temperature=temperature, tools=tools)
        tool_calls = msg.get("tool_calls") or []
        if not tool_calls:
            # 3) 首轮无工具:直接返回内容,让 Runner 走流式
            if msg.get("content") and not any_tool_used:
                return working, str(msg["content"])
            break

        # 4) 把 assistant 消息(含 tool_calls) 追加到 messages
        any_tool_used = True
        working.append({"role": "assistant", "content": msg.get("content"), "tool_calls": tool_calls})

        # 5) 真正执行每个 tool,并把结果以 tool role 回填
        for tc in tool_calls:
            fn = tc.get("function") or {}
            name = fn.get("name") ""
            args = parse_tool_arguments(fn.get("arguments"))
            tc_id = tc.get("id") or f"call_{round_i}_{name}"
            try:
                result = await execute_interview_tool(name, args, db=db, ...)
            except Exception as tool_exc:
                result = f"工具执行失败: {tool_exc}"
            working.append({"role": "tool", "tool_call_id": tc_id, "content": result})

        # 6) 下一轮 LLM 看到结果,可能继续 tool_calls 或输出文本
    return working, None

4Embedding & 向量检索

AI 基础

核心概念

Embedding = 把文本映射到高维向量(如 1536 维),使"语义相似"的文本在向量空间中距离近。检索时计算 query 向量与所有文档向量的余弦相似度(cosine),取 top-K。

常见坑

  • 把过多文档塞进 prompt → 噪声大,精度反而下降
  • 切片太粗(一段 5k 字)→ 检索出"主题相关但细节不相关"的文档
  • 切片太细(每句一片)→ 失去上下文
  • embedding 模型与 query 用不同模型 → 向量空间不一致

5RAG 原理与切片

AI 基础

核心概念

RAG(Retrieval-Augmented Generation) = 在 LLM 生成前,先用 query 从知识库中检索出相关文档,把"问题 + 相关文档"一起塞进 prompt。优势:① 注入领域知识;② 减少幻觉;③ 数据可更新而不重新训练模型。

切片策略示例

interview_service/capabilities/rag/_kb_data.py_build_documents
def _build_documents():
    texts, metadatas, ids = [], [], []
    for company in BUILTIN_COMPANIES:        # 7 家公司
        cid = company["id"]
        # 切片 1:style         切片 2:focus_areas
        # 切片 3:每题一片    切片 4:interview_flow
        texts.append(f"{company['name']}({cid})面试风格:{company['style']}。压力等级:{company['pressure_level']}。")
        metadatas.append({"company_id": cid, "company_name": ..., "section": "style"})
        ids.append(f"{cid}::style")

        texts.append(f"{company['name']}考察重点领域:{', '.join(company['focus_areas'])}。")
        metadatas.append({..., "section": "focus_areas"})
        ids.append(f"{cid}::focus_areas")

        for idx, q in enumerate(company["sample_questions"]):
            texts.append(f"{company['name']}典型面试问题示例:{q}")
            metadatas.append({..., "section": "sample_question", "question_index": idx})
            ids.append(f"{cid}::q::{idx}")

        texts.append(f"{company['name']}典型面试流程:{company['interview_flow']}")
        ids.append(f"{cid}::flow")
    return texts, metadatas, ids

每条 metadata 携带 company_id,检索时可以 where={"company_id": "bytedance"} 限定到当前目标公司。

RAG vs 其它增强

方式优点缺点
RAG(检索增强)知识可更新、可解释依赖检索质量
Fine-tuning改变模型"行为"成本高、难迭代
Long context简单,直接拼贵,易注意力衰减
Tool calling(查 DB/查 API)结构化、确定性需要后端配合

async def _retry_request(coro_factory, *, max_retries=3, backoff=0.5, is_stream=False):
    # 429 / 5xx 指数退避;4xx 直接抛
    for attempt in range(max_retries + 1):
        try: resp = await coro_factory()
        except httpx.HTTPStatusError as e:
            sc = e.response.status_code
            if sc == 429 or sc >= 500:
                if attempt < max_retries:
                    if is_stream:
                        try: await e.response.aclose()
                        except: pass
                    await asyncio.sleep(backoff * (2 ** attempt))
                    continue
            raise
        if resp.status_code == 429 or resp.status_code >= 500:
            if attempt < max_retries:
                await asyncio.sleep(backoff * (2 ** attempt))
                continue
            resp.raise_for_status()
        return resp

def compress_messages(messages, max_tokens, *, keep_recent=20, threshold=0.3):
    total = estimate_messages_tokens(messages)
    if total <= max_tokens * threshold: return messages  # 不超阈值不压
    system = [m for m in messages if m.get("role") == "system"]
    rest = [m for m in messages if m.get("role") != "system"]
    trimmed = rest[-keep_recent:]
    # 在 system 段末尾追加"已压缩"说明,让 LLM 知道
    summary = {"role": "system", "content": f"[上下文压缩] 早期 {len(rest) - len(trimmed)} 条对话已省略,保留最近 {len(trimmed)} 条。"}
    return system + [summary] + trimmed

9ReAct 与工具循环

Agent 模式

核心概念

13Reflection / Self-Critique

Agent 模式

核心概念

让 LLM 在生成结果后,自己再"审视"一遍,找出错误并改进。变体:Self-Refine(自我批评+自我修改)、CrewAI(多 agent 互评)、Constitutional AI(按原则评)。

RealMock 的"轻量级反思"

16Hooks 规则与心智模型

React

核心概念

Hook 是 React 16.8 引入的"在函数组件中使用 state 与副作用"的机制。规则只有两条(违反会爆):

  1. 只在最顶层调用 Hook(不要在 if/for/嵌套函数里)
  2. 只在 React 函数中调用(函数组件或自定义 Hook)

每次组件渲染,React 维护一个Hook 链表(单向链表,实现上是数组),按调用顺序:[Hook1 → next → Hook2 → next → ...]。每次 useState 创建一个节点,记录 value 和 setter;每次 useEffect 创建一个节点,记录 effect 函数和依赖数组。

21重渲染优化

React

React 触发重渲染的时机:① setState;② 父组件重渲染;③ Context value 变。

3 把武器

  • React.memo:子组件用 memo 包裹,只在 props 变化时重渲染
  • useCallback:缓存函数引用,避免子组件的 memo 失效
  • useMemo:缓存计算结果(如大列表的 filter/sort)

✅A

Token 是 LLM 的最小处理单元,由 BPE 等算法切出。常见估算:中文 1 字 ≈ 1.5 token,英文 1 词 ≈ 1.3 token。1.5 这个估值是因为中文字符在 BPE 编码中平均被切成 1~2 个 token(常用字 1 个,生僻字 2~3 个)。

为什么估值就够:精确 token 数需要跑对应模型的 tokenizer,代价大。估值用于"预算检查",不会影响功能。RealMock 在 context_manager.py 用 1.5 估算 context 占用,在 30% 阈值就触发压缩,留足安全边际。

❓Q2. Prompt Engineering 常见坑与最佳实践?

✅A

坑:① 只靠自然语言约束(模型会"忘");② 规则之间冲突;③ 系统 prompt 超长(挤占对话上下文);④ 假设模型"知道"上下文(它不会跨请求)。

实践:① 结构化输出(JSON schema / response_format);② 每个 prompt 末尾追加 hard constraint(如 RealMock 的 with_agent_output_rules);③ 少示例好过多示例;④ 用 [PHASE_COMPLETE] 这类机器可读标记而非让 LLM 自然语言输出状态。

❓Q3. Function Calling 的工作流程?为什么 LLM "调工具"不是真执行?

✅A

流程:① 应用把 tools 描述发给 LLM;② LLM 在生成回复时决定调哪个工具、把什么参数,以 tool_calls JSON 返回;③ 应用真的执行工具;④ 把结果以 role: tool 消息回喂给 LLM;⑤ LLM 在下一轮继续。

为什么不是真执行:① LLM 沙箱化,不能访问文件系统/网络;② 工具可能副作用(扣款、删 DB),LLM 不该有权限;③ 应用层能加限流、鉴权、审计。

❓Q6. 流式响应断了怎么办?如何重试?

❓Q13. 为什么 Hook 不能写在 if 里?

✅A

React 用调用顺序来匹配每个 state 和 effect 到正确的"槽位"。如果 Hook 调用顺序变了,React 会把这次的 state 误认为是上次的,数据就串了。

这是 React 选择 Hook 链表(而不是 HashMap/WeakMap)的根本原因——简单、显式、易理解。

❓Q14. useEffect 的清理函数什么时候执行?

✅A

① 组件卸载时;
② 下次 effect 跑之前(deps 变化时,先 cleanup 旧的,再跑新的);
③ Strict Mode 开发环境:挂载 → 卸载 → 重新挂载(故意双调用)。

RealMock 的 useInterviewWS 在 cleanup 中:generationRef.current += 1 + ws.onclose = null; ws.onerror = null; ws.onmessage = null + ws.close(1000, "client_cancel")。

❓Q15. useRef 和 useState 的区别?

✅A

useState 改值触发重渲染,useRef 改 .current 不触发。
原则:需要显示在 UI 的 → useState;计时器 ID、WS 实例、回调引用、上一次的 props/state → useRef。
RealMock 的 useTTSPlayer 用 11 个 ref + 仅 2 个 state,把"不需要触发重渲染"的状态全放 ref。

❓Q16. React Strict Mode 故意双调用 effect,怎么防止 WS 无限重连?

✅A

用 generationRef。每次 effect 跑时 generation = ++generationRef.current。所有异步回调里判断 generationRef.current === generation,不一致就丢弃。cleanup 时 generationRef.current += 1 让旧 effect 的所有回调失效。

RealMock 的 useInterviewWS 还加了一个保险:判断 wsRef.current !== ws(实例相等)。两层保护防止任何 race。

❓Q17. 什么时候用 useMemo / useCallback?什么时候不用?

✅A

用:① 给 React.memo 子组件传稳定 props(避免子组件失效);② 大列表的 filter / sort / dedupe(否则每次 render 重算);③ 创建昂贵的对象(订阅、IO 资源)。
不用:① 小列表(100 项以下);② 简单 JSX;③ 一次性事件 handler(子组件本来就会 re-render)。
原则:先正确,后优化。用 React DevTools Profiler 看实际开销再决定。

❓Q18. WebSocket 怎么设计断线重连?

✅A

① 指数退避:1s → 2s → 4s → 8s(上限);
② 最大重试次数:5 次后切"failed"状态;
③ 长间隔保活:失败后 20s 一次;
④ 主动重置:用户可手动 retry;
⑤ 网络感知:navigator.onLine 监听;
⑥ 区别关闭原因:code 1000 + 正常 reason → 不重连;异常 code → 重连。

❓Q19. 浏览器怎么录音并以 base64 上行?

✅A

① navigator.mediaDevices.getUserMedia({audio: true}) 拿 MediaStream;

⑤ 重采样到 16kHz;

❓Q21. Next.js App Router 与 Pages Router 区别?

❓Q25. FastAPI 依赖注入(Depends)的工作原理?每次请求都会调用吗?

❓Q26. asyncio.gather vs asyncio.create_task 区别?

✅A

create_task:fire-and-forget,返回 Task,不阻塞当前,异常会"丢失"(变 Unhandled);
gather:等待所有任务完成,返回结果列表,任一异常会立刻传播(除非 return_exceptions=True)。

RealMock 工具循环用 asyncio.gather(*[self._run_tool_call_safe(tc, db) for tc in limited]) 并发执行;后台任务用 create_task + 自行 add_done_callback 处理异常。

✅A

❓Q28. SQLAlchemy Session 是线程安全的吗?Web 怎么处理?

✅A

不。Session 不是线程安全的。Web 框架的标准做法:每个请求一个 Session(request-scoped),在请求结束(无论成功失败)关闭。

❓Q29. SQLAlchemy 中 with_for_update() 是什么?SQLite 支持吗?

✅A

SELECT ... FOR UPDATE:悲观锁,锁定 SELECT 出的行,事务结束才释放。
SQLite 通过 整个数据库的写锁(BEGIN IMMEDIATE)模拟,会阻塞所有写。PostgreSQL/MySQL InnoDB 是行级锁。
RealMock 简历激活用 with_for_update(),因为 SQLite 单写所以不会真并发,但代码跨库可移植。

❓Q30. SQLite WAL 模式为什么能并发读写?

✅A

默认 rollback journal 模式下,写时把原页写到 -journal、锁库、写。读阻塞直到写完。
WAL(Write-Ahead Log)模式:写追加到 -wal 文件(顺序写,极快),不阻塞读。读先看 wal 再看主文件,得到一致快照。
代价:wal 文件需 PRAGMA wal_checkpoint 定期合并;突发大量写时 wal 变大。
RealMock 用 PRAGMA journal_mode=WAL + busy_timeout=5000 + synchronous=NORMAL。

❓Q31. AES-GCM 的 nonce 重复会怎样?

✅A

灾难性。GCM 安全性基于"nonce 唯一",如果同一 (key, nonce) 加密两个不同明文:① 攻击者可恢复明文异或;② 可伪造认证 tag。等于完全失守。

RealMock 的 encrypt_secret 用 os.urandom(12) 生成 nonce(96 bit 随机,生日攻击需要 2^48 次才碰撞),实际安全。

❓Q32. PBKDF2 是什么?为什么 RealMock 用 200k 迭代?

✅A

PBKDF2(Password-Based Key Derivation Function 2)用 HMAC-SHA256 + 盐 + 大量迭代,把弱密码(或短 key)派生为强 32 字节 AES 密钥。
200k 迭代是 OWASP 2023 推荐的下限,目的是让单次派生耗时 ~250ms(防暴力)。如果 1k 迭代,GPU 可每秒跑 ~10^8 次;200k 后降到 ~500 次。
RealMock 通过 hashlib.pbkdf2_hmac("sha256", master, salt, 200_000, dklen=32) 派生。

❓Q33. SSRF 怎么防?DNS rebinding 怎么破?

✅A

SSRF 防御:① URL 解析 + 黑名单网段(127/10/172.16/192.168/169.254);② 多 A 记录遍历,任一不安全即拒;③ 协议限定 http/https;④ 端口限定 80/443;⑤ prod 强制 https。
DNS Rebinding:攻击者 DNS 第一次返回公网 IP(通过校验),第二次返回 127.0.0.1(实际建连)。
破解:DNS Pin。RealMock 的 make_pinned_async_client 单次解析后,把 IP 写进 PinnedHostTransport,后续连接固定用该 IP,Host 头保留原 hostname。

❓Q34. 限流算法有哪些?RealMock 用哪种?

✅A

固定窗口(临界双倍)/ 滑动窗口(精确)/ 令牌桶(支持突发)/ 漏桶(严格平滑)/ 滑动日志(精确但内存大)。

❓Q35. 进程内锁 + DB 哨兵 两层防双打怎么实现?

✅A

场景:WS 自动 finish + HTTP 手动 /finish + 报告页 GET,三路并发触发报告生成。

进程内锁:asyncio.Lock 字典 {session_id: lock},同进程内串行。
DB 哨兵:UPDATE session SET report = '{"_generating":true}' WHERE id = ? AND report IS NULL OR '{}',谁 UPDATE 成功谁拿到任务。
失败清理:任何路径异常都 UPDATE ... SET report = '{}' 清掉哨兵,避免永久卡住。
轮询:抢不到哨兵的路径 sleep 0.2s × 30 次,等别人写完。
这是工业级的"跨进程 + 跨 worker"并发模式。

❓Q36. 什么是 capability token(能力令牌)?和 session 的区别?

✅A

Q37-Q48传统 CS 面试题

面试题

❓Q37. 进程 vs 线程 vs 协程?

✅A

进程 = OS 调度,独立地址空间,通信靠 IPC;线程 = OS 调度,共享堆,通信靠共享变量(需锁);协程 = 用户态 runtime 调度,单线程上的合作式多任务。
Python 因 GIL,CPU bound 只能多进程;IO bound 用 asyncio 协程最高效。
内存:进程 MB 级 / 线程 KB 级 / 协程几 KB。

❓Q38. TCP 三次握手为什么不是两次?

✅A

两次只能确认"客户端发 + 服务端收"。无法确认客户端"能收到服务端发的"。三次后双方都确认了"双向可达"。
防止"失效的连接请求报文"被服务端误接收(网络延迟下旧 SYN 报文可能迟到)。

❓Q39. HTTP 1.1 流水线 vs HTTP 2 多路复用?

✅A

HTTP 1.1:同一连接同一时刻只能处理 1 个请求(响应未完不能发下一个);
HTTP 1.1 流水线:同一连接可连续发,但响应顺序必须一致(队头阻塞);
HTTP/2:同一连接多路复用,每个请求带 stream id,响应可乱序(用 id 重组),彻底解决队头阻塞。

❓Q40. 数据库 4 种隔离级别,RealMock 关注什么?

✅A

Read Uncommitted / Read Committed / Repeatable Read / Serializable,分别对应"脏读/不可重复读/幻读"的逐步禁绝。
RealMock 用 SQLite,默认 Serializable(SQLite 的实现是全库锁)。所以 RealMock 不需要担心幻读;真正的并发控制靠进程内 asyncio.Lock + DB 哨兵。

❓Q41. 乐观锁 vs 悲观锁?

✅A

悲观锁(SELECT ... FOR UPDATE):先取锁,操作,提交;冲突概率高时高效。
乐观锁(UPDATE ... WHERE version = ?):不加锁,提交时检查 version 是否变化;冲突概率低时高效。
RealMock 简历激活用悲观锁(with_for_update),因为激活是低频关键操作。报告生成用乐观锁思想(哨兵 CAS)。

❓Q42. LRU 缓存怎么实现?

✅A

HashMap + 双向链表:HashMap 给 O(1) 查找,双向链表维护访问顺序(头部最新,尾部最旧),容量满时淘汰尾部。
Python 直接用 @functools.lru_cache(maxsize=128)。
RealMock:① get_settings 用 @lru_cache;② _master_bytes(secrets)用 @lru_cache;③ Whisper 模型用模块级 _whisper_model + set_whisper_model 切换。

❓Q43. 一致性哈希?为什么需要?

✅A

普通 hash(key) % N 在 N 变化时(加/减节点)几乎所有 key 都要重新映射(缓存雪崩)。
一致性哈希:把 hash 值映射到 0~2^32 圆环,节点也映射到圆环,key 沿环找到最近的节点。增删节点只影响相邻一小段。
常用于分布式缓存(Redis Cluster、Memcached)、CDN、负载均衡。

❓Q44. 什么是漏桶 vs 令牌桶?

✅A

漏桶:请求排队,固定速率出。无法应对突发(超出的请求直接拒绝或排队到天荒地老)。
令牌桶:固定速率往桶里加 token,每个请求消耗 1 个。允许"突发"(桶里有 N 个 token 可一次性放过 N 个请求,适合"刚启动时跑批")。
Guava RateLimiter / Sentinel 都用令牌桶。

❓Q45. CAP 定理为什么只能二选一?

✅A

P(分区容忍)必选:实际网络一定会分区(交换机断、机房断网)。
分区时:要 C(强一致)→ 拒绝部分写/读,失去 A;要 A → 各节点独立服务,牺牲 C(暂时不一致)。
所以现实系统是 AP + 最终一致(如 DynamoDB / Cassandra)或 CP(如 etcd / ZooKeeper,部分不可用)。

❓Q46. Raft 与 Paxos 区别?

✅A

Paxos 太晦涩难懂,各种变体难以推理。Raft 设计目标 = 易理解:① 强领导(任何时候最多 1 个 leader);② 任期(term)单调递增;③ 日志复制 = leader 把日志条目发到所有 follower,过半确认才提交。
Raft 三子问题:领导选举、日志复制、安全性。
etcd / Consul / TiKV 都用 Raft。

❓Q47. 什么是 2PC?它阻塞在哪?

✅A

两阶段提交:① 协调者问所有参与者"能不能提交",参与者锁资源写日志回 OK;② 协调者发"提交",所有参与者提交。
阻塞点:协调者在第一阶段后崩溃 → 参与者锁了资源但没人说"提交还是回滚",永久阻塞。
3PC引入预提交+超时,但仍有边界情况(网络分区)。
实际:分布式事务普遍用最终一致(Saga / 事件溯源)而非 2PC。

❓Q48. 什么是 TLS 1.3 的 0-RTT?

✅A

传统 TLS 1.2 至少 2-RTT(握手 + 密钥交换)。
TLS 1.3 简化为 1-RTT(客户端在第一帧就发密钥共享)。
0-RTT:如果客户端之前连过,可在第一条消息就发加密数据(用 PSK 密钥)。代价:可重放攻击(中间人重发第一帧),所以只用于幂等请求(如 GET)。

Q49-Q60系统设计 / 综合面试题

面试题

❓Q49. 如何设计一个"实时面试"系统?说出主要模块和挑战。

✅A

模块:① API 网关(CORS / 限流 / 鉴权);② WebSocket 服务(长连接 / 心跳 / 消息分发);③ LLM 引擎(流式 + 工具循环);④ STT 服务(麦克风转文字);⑤ TTS 服务(文字转语音);⑥ 报告服务;⑦ 候选人档案 + 简历存储。
挑战:① 流式响应断在中间的容错;② WS 多标签页顶替;③ 候选人打断面试官的全双工;④ 报告三路并发(WS/HTTP/GET)的防双打;⑤ 思考 LLM Key 与 ASR Key 隔离;⑥ 隐私(PII、SSRF)。

❓Q50. 上下文压缩的 4 种策略?RealMock 用哪种?

✅A

① 滑窗(留最近 N 条);② 摘要(LLM 总结早期);③ Token 截断;④ 语义聚类(embedding 去重)。
RealMock 用① + ② 的简化版:阈值 30% 触发,留 system + 最近 20 条 + "已压缩"说明。摘要版成本高,通常作为离线预处理。

❓Q51. 如何让 Agent "有记忆"?

✅A

① 短期(messages):当前会话,可能压缩;② 长期(DB / 文件):跨会话持久化,如用户偏好、历史摘要;③ 结构化(字段而非全文):如 weak_points、asked_questions,让 LLM 知道在哪写在哪读;④ 检索(RAG):把相关记忆当工具调出来。
RealMock 三层都用:agent_state 字段、prep_sessions.messages、system_learning.json 跨场次反哺。

❓Q52. WebSocket 心跳怎么设计?为什么 30s?

✅A

① 服务端每 30s 发 ping;② 客户端 30s 内没收到任何消息 → 主动 ping;③ 累计 3 次未响应 → 关闭连接。
为什么 30s:① 太短浪费流量;② 太长发现断线慢;③ 主流 LB(Nginx / Cloudflare)默认 60s idle timeout,留 30s 缓冲。
RealMock 客户端 30s + 3 次 miss ≈ 90s 才发现断线,生产可接受。

❓Q53. 如何防止 LLM API Key 泄漏?

✅A

① BYOK 加密落库(AES-256-GCM + PBKDF2 派生 + master key 环境变量);② 出站前脱敏(RedactFilter 在 logging 中替换 sk-/Bearer);③ 不存前端(Cookie HttpOnly + Secure + SameSite=Lax);④ SSRF 防御(不让用户控制出站 URL,无法通过 DNS 探测偷取);⑤ 旧格式检测(enc:v1 拒绝静默迁移,要求用户重存);⑥ 轮转(定期更换 master key + 用户重存)。

❓Q54. 为什么 RealMock 不用 Postgres?SQLite 的极限在哪?

✅A

本地优先、零运维、文件即库,适合个人/小团队。SQLite 上限:① 单写者(WAL 后读不阻塞写,但写仍串行);② 无网络(库文件锁);③ 表 ≤ ~ 1 亿行/库;④ 无复杂类型(enum/json 字段都是文本);⑤ 无内置复制/分片。

切到 Postgres 的信号:① 并发写入 ≥ 5/s;② 数据量 > 100GB;③ 需要跨实例访问。RealMock 用 SQLAlchemy 2.0 + 抽象 get_engine() 即可平滑迁移。

❓Q55. 单页面 940 行的"上帝组件"如何重构?

✅A

① 按业务域切(features/interview/{hooks,components}):
  - useInterviewRoom:会话生命周期 + 消息 + 阶段
  - useInterviewAudio:录音 + TTS
  - useInterviewHints:参考提纲
② 组件切:ChatPanel / ControlBar / AvatarStage / VideoPanel;
③ 页只做组装:return <ChatPanel /> <ControlBar /> ...;
④ 状态按生命周期分:useReducer 管复杂状态机,useState 管局部;
⑤ 避免 Context(全用 props + hooks 传)。

❓Q56. 实时系统的"数据一致性"如何保证?

✅A

RealMock 场景:WS 写状态、报告生成、GET 报告页三路并发。保证:

① 幂等:同一操作可重入不破坏状态(报告生成用 CAS 哨兵);
② 状态机:状态转移有合法集合(pending → active → completed);
③ 锁:进程内 asyncio.Lock + DB 哨兵;④ 最终一致:不追求"看到 100% 准确",允许短暂不一致(报告生成中显示空,GET 拉取后展示)。

❓Q57. 系统设计:"弹幕 + 直播"怎么设计?

✅A

① 弹幕读取:长轮询(简单) / SSE(单向流,HTTP 友好) / WebSocket(双向);生产选 WebSocket。
② 弹幕发送:HTTP POST,经消息队列(Kafka)异步分发;
③ 推 vs 拉:百万级同时观看 → 推(每条弹幕 fanout 到所有连接);千万级 → 拉(每客户端每 N 秒拉一次);
④ 反垃圾:限流(每用户 1 条/秒)+ 敏感词过滤;
⑤ 弹幕"飞过"动画:客户端 CSS transform: translateX(0) → translateX(-100%),requestAnimationFrame 驱动。

❓Q58. 估算一个 LLM 服务的"成本上限"如何做?

✅A

① 单次成本 = prompt_tokens × input_price + completion_tokens × output_price;
② 用户数 × 平均会话数 × 平均回合 × 平均 tokens;
③ 加 buffer 30% = 系统 prompt + 工具结果 + 压缩失败重试;
④ 限流配额(每用户 10/min)+ 告警;
⑤ 自建 token 计数器 + Prometheus 指标;
⑥ RealMock 限流策略:LLM 10/min、session_create 20/min,正好对应"防 DoS"和"防误用"双层。

❓Q59. 微服务 vs 模块化单体?RealMock 选了哪个?

✅A

微服务:独立部署、独立伸缩、技术栈异构;代价:运维复杂度、分布式事务、网络不可靠、跨服务追踪。
模块化单体:一个进程,模块边界清晰,各自 main.py 可独立启动,演进到微服务时改 base URL 即可。
RealMock 选模块化单体:api_service / agent_service / interview_service 业务零循环,仅共享 shared/。每个服务都有独立 main.py,未来要拆只改部署。

❓Q60. 你会怎么测试一个 LLM 应用?

✅A

① 单测:工具函数(检索、解析、压缩)、纯逻辑(followup.analyze);
② 集成:test_main.py 测整链路 + sessions/test_session_* 测 WS;
③ Contract 测试:用 fake LLM(预先录制响应)测"如果 LLM 返回 X,系统行为 Y";
④ 稳定性:固定 seed、相同输入多次跑结果一致;
⑤ 回归:用上一版本的"好回答"做基准集;
⑥ Eval:services/tests/test_review_hardening.py 做了 prompt 与错误码覆盖;
⑦ 前端:核心 hook + 关键页面 单元测试 + 关键路径 E2E(Playwright);
⑧ 不要:测 LLM 的"答案质量"作为单测(主观、漂移、贵)——交给人工抽检。
